# Contributing to illume

Thanks for considering it. This file says what the project expects, so that a
contribution is not turned away for a reason nobody told you.

## Reporting a bug

Open an issue with a **reproducible example** — the smallest script that shows
the problem, with `set.seed()` if it involves simulation, plus the output of
`sessionInfo()`.

If the bug is that a model gives the wrong answer, say what you compared it
against. That is not a formality: every defect this package has had was found
by comparing against an outside implementation or by widening a simulation, and
none was found by the test suite. A report that says "illume gives 0.42 and
`glmmTMB` gives 0.51 on this data" is worth more than a long description.

## Proposing a feature

Open an issue before writing code. Two questions get asked of anything new:

1. **Does it need a new hard dependency?** The answer has to be no. A package
   in `Suggests`, used behind `requireNamespace()`, is fine.
2. **If it is a diagnostic, what remedy does it name?** Every check in this
   package names a fix that exists *in this package*. A diagnostic that reports
   a problem and leaves the user to find the answer elsewhere is a complaint,
   and will not be merged as one. Where the remedy did not exist, it was built
   first.

## Making a change

- Branch from `main`, one change per pull request.
- `devtools::document()` after touching roxygen. Committed `man/` must match.
- `devtools::test()` must pass. The suite takes about half an hour.
- `devtools::check()` must be clean. CI runs it on Linux, macOS and Windows
  against R release, devel and oldrel.
- Match the surrounding code: `ilm_` prefix on exported functions, en-GB
  spelling, comments that say *why* rather than *what*.

## Claims and evidence

A statement about how the package behaves belongs in `studies/`, not in a
sentence. If a change alters a number that appears in the documentation — a
coverage rate, a timing, an agreement tolerance — the study that produced it is
re-run and the generated findings file is updated with it. Findings are
generated by `studies/scripts/summarise_run.R` and are never hand-written.

Do not commit raw `.rds` output from a study run. `.gitignore` excludes it, and
the study scripts use fixed seeds so it can be regenerated exactly.

## Using generative AI

Permitted, and disclose it. Say in the pull request which tools you used and
what for. You are responsible for reviewing and validating anything they
produced, and for the design decisions either way.

This is not a rule imposed on contributors from outside it: the package itself
was drafted in collaboration with a language model under human direction, and
says so in the README. The standard asked of a contribution is the standard the
package holds itself to -- that a claim about behaviour comes with a
measurement, and that the measurement is against something somebody else
wrote.
